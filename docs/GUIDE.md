# WatchCat（看门猫）

![WatchCat](../assets/mascot/watchcat-logo-1536.png)

> 原名 watchDog。程序文件、计划任务和数据文件夹暂时沿用原来的名字（WatchDog.exe、MemWatchdog.ps1 等），升级后不用重新设置。

Windows 内存泄漏"体检 + 修复"工具：程序内存泄漏、驱动（内核内存）泄漏、句柄和图形资源（GDI / USER）泄漏都能发现。

任务管理器只能告诉你**现在谁占得多**；WatchCat 回答的是：**谁在变坏、为什么、怎么修**。

不需要安装任何依赖：监控窗口 `WatchDog.exe` 是 C# 写的，用 Windows 自带的 .NET Framework 4 编译器生成，独立运行；后台看门猫和修复脚本是 PowerShell 脚本（Windows 10 / 11 自带），每次只运行几秒。

![主界面：整机内存走势、体检结论、按问题排序的程序列表](main.png)

## 下载

到 [Releases](https://github.com/yifanwow/watchDog/releases) 下载最新的 `WatchDog-v版本号.zip`，解压到一个固定的文件夹，双击 `WatchDog.exe` 就能用，不用安装任何东西（需要 Windows 10 / 11）。

- 程序没有付费的代码签名，第一次打开时 Windows 可能提示"已保护你的电脑"：点"更多信息" → "仍要运行"。
- 解压后不要再挪文件夹：看门猫的计划任务会记住这个位置。
- 也可以自己从源码编译：见下面的"使用"。

## 和任务管理器有什么区别

| | 任务管理器 | watchDog |
|---|---|---|
| 看到的 | 此时此刻的占用 | 近 30 分钟 / 1 / 3 / 12 / 24 小时的走势：内存、CPU、磁盘、每个程序 |
| 看不到的 | 驱动占的内存、句柄和 GDI 一直涨 | 内核内存池（驱动用的内存）走势，能指出是哪个标签 / 哪个驱动在涨；每个程序的句柄数、GDI / USER 对象数和走势 |
| 能告诉你 | 谁占得多 | 每个程序是 **稳定 / 波动大 / 缓慢上涨 / 疑似泄漏**，并预测"照这个速度会涨到多少"。窗口打开 10 分钟就有初步判断 |
| 遇到问题 | 只能"结束任务" | 命中**问题规则库**时给出原因说明和对应的修复方法（重启程序 / 重启服务 / 重建文件） |
| 你不在电脑前 | 什么也不做 | 看门猫每 10 分钟自动检查，按规则自动修复 |
| 自身负担 | 打开就卡 | 后台检查每 10 分钟跑约 5 秒就退出；窗口只在打开时运行 |

## 包含什么

| 文件 | 作用 |
|---|---|
| `Build-Release.ps1` | 打下载包：编译后把 exe 和需要的脚本打成 `release/WatchDog-v版本号.zip`（只放白名单里的文件，个人数据不会进去） |
| `Build-Exe.ps1` | 把 `src/` 里的 C# 代码编译成 `WatchDog.exe`，并生成图标（exe 不进 git，自己生成） |
| `WatchDog.exe`（源码在 `src/`） | **监控窗口**（赛博朋克风格：红黑底 + 荧光蓝）。顶部内存（大卡片，含占用最多的程序）/ CPU / 磁盘 / 内核卡片；右侧"体检结论"上方是看门猫的状态和"心跳"（最近每次后台检查），下面直接告诉你电脑是否健康、有哪些问题；程序列表默认把有问题的排在最前；选中程序可看 24 小时曲线、原因和修复按钮 |
| `MemWatchdog.ps1` | **看门猫**：按规则检查，`auto: true` 的规则命中时自动修复；同时记录历史数据给监控窗口用 |
| `rules.json` | **公共问题规则库**：已知问题的"症状 → 原因 → 修复方法" |
| `rules.local.json` | **你自己的规则**（不进 git）。第一次在窗口里点"编辑我的规则"时会从 `rules.local.example.json` 复制一份 |
| `Install-Watchdog.ps1` | 把看门猫安装为计划任务（每 10 分钟 + 登录时运行）。加 `-Uninstall` 卸载。也可以在窗口里一键安装 |
| `Fix-NvTopps.ps1` | 重建膨胀的 NVIDIA `nvtopps.db3` 数据库（只保留一份备份 `nvtopps.bak`） |
| `Capture-Handles.ps1` + `HandleProbe.cs` | 记录句柄现场：某个程序句柄暴涨时，把它手里的句柄（注册表键路径、线程从哪个模块启动……）和当时的电源 / 屏幕事件写成一份文本（看门猫自动调用，也可以手动） |
| `Analyze-Leak.ps1` + `LeakProbe.cs` | 分析内存泄漏：看一个程序在忙什么（抓最忙线程的调用栈）、漏的是什么（内存里重复最多的内容）、最近 24 小时涨多快，写成一份带自动解读的报告（右键程序 → 分析内存泄漏） |
| `Restart-Aura.ps1` / `Restart-GHub.ps1` / `Restart-SteamWeb.ps1` | 重启华硕灯效并让奥创中心重新下发原来的灯效 / 只重启罗技 G HUB 的后台和托盘（按开机方式启动，不弹窗口）/ 只重启 Steam 的网页界面（Steam 本身不动），并确认都回来了 |
| `Restart-Group.ps1` | 按顺序重启一组进程 / 服务（`restartGroup` 规则和规则向导用），进程按原来的路径和参数重新打开 |
| `Restart-ServiceHard.ps1` | 安全地重启服务：卡在"正在停止"时强制结束，但只在该服务独占进程时才这么做，不会误伤同一进程里的其他系统服务 |
| `extras/SonicStudio*` | （可选，仅华硕 Sonic Studio 用户）一键开关 Sonic Studio |

## 使用

1. 第一次使用：右键 `Build-Exe.ps1` → 用 PowerShell 运行，生成 `WatchDog.exe`（用 Windows 自带的 C# 编译器，不下载任何东西）。以后双击 `WatchDog.exe` 打开监控窗口；也可以右键它"发送到桌面快捷方式"或固定到任务栏。`WatchDog.exe` 要和其他脚本放在同一个文件夹里（它读这里的规则和记录，修复时也调用这里的脚本）。更新代码后重新运行一次 `Build-Exe.ps1`：如果 WatchDog 正在运行，它会先让 WatchDog 存好数据退出（`WatchDog.exe --exit`），编译完再重新打开。
2. 点右下角操作区的"设置"，打开"后台看门猫"开关，确认管理员权限。
3. 窗口打开 10 分钟后给出初步稳定性判断；看门猫记录满 1 小时后给出长期判断（包括"疑似泄漏"）。
4. 走势图默认显示**整机内存、近 30 分钟**。点顶部的 **内存 / CPU / 磁盘 / 内核** 卡片、或右侧的看门猫面板切换内容；点列表里的程序，看这个程序的走势。右上角可选近 **30 分钟 / 1 小时 / 3 小时 / 12 小时 / 24 小时 / 7 天**：1 小时以内用窗口的实时数据（5 秒一个点），3–24 小时用看门猫的记录（10 分钟一个点），7 天按小时汇总（程序取每小时的最低值，看"底线"有没有一直往上抬）。看门猫最近一次记录之后的那一段，接的是窗口的实时数据，所以长范围的最右边也一直是"现在"（比如刚重启清空的程序，马上就能看到掉下来）。
   看门猫在管的程序（有专项修复规则）单独放在列表上方的**重点监控**区块，名字右边有一个**像素十字**（黑色小方块里四个像素拼成的十字），颜色表示它现在的状态：正常色（来生主题是蓝、摩羯 / 旧梦是绿）= 正常，黄 = 需要留意，红 = 出问题（超过上限等，看门猫会在你空闲时处理，或者提醒你）。
5. **所有提示、确认、输入框和规则 / 记录窗口都是同一套红黑界面**，不再弹系统对话框。
6. **发现的问题可以"忽略"或"确认正常"**：体检结论里每个问题右边有两个小按钮，右键程序也可以。"忽略"是 24 小时内不提醒；"确认正常"是以后不再提醒，规则发现的问题看门猫也不会再自动处理。记录在 `ignore.json`（个人设置，不进 git），"操作"里的"已忽略"可以一键恢复。
7. 标题栏中间显示**自身占用**：看门猫每次后台运行多久、用了多少 CPU 时间、峰值内存，以及本窗口的内存 / CPU。
8. **托盘图标一直都在**；点关闭或最小化只是把窗口藏到托盘，在后台继续每 5 秒记录（打开和藏起来时记录的数据完全一样，只是藏起来时不画界面）。点托盘图标重新打开（如果窗口原来所在的显示器已经关掉或拔掉，会挪到鼠标所在的屏幕上打开）；**要退出：右键托盘图标 → 退出**。只会开一个：已经在运行时再双击 `WatchDog.exe`，会把原来的窗口叫出来。任务栏显示 WatchDog 自己的图标，可以固定到任务栏。
   **看板娘 Fegmi**：主窗口右边站着 WatchCat 的看板娘 Fegmi（素材在 `assets\mascot\`，以 `parts.json` 为入口：每个部件一张 512×1024 对齐的透明 PNG，同一组的换帧用 `slot` 标出来）。默认大小是主窗口高度的 60%，设置里「Fegmi 的大小」可以在 0.7–1.7 倍之间调。她会眨眼，帽子和帽尖的星星会轻轻摆，故障残影偶尔闪一下；第一次出现时挥手打招呼；体检发现新问题时在头顶冒气泡说出来（皱眉、担心的嘴型），说好消息时笑眯眯；点气泡会选中那个程序，点她会挥手并说说现在的情况。按住拖动可以换位置（记住和主窗口的相对位置），右键可以回到默认位置或让她休息，设置里「召唤 Fegmi」可以开关。她跟着主窗口移动，主窗口缩到托盘或最小化时一起藏起来，动画定时器也停掉；平时每秒最多画 10 帧，姿势没变就不画。

   动画都是换帧：眨眼（eyes-half → eyes-closed → eyes-half）、说话（mouth-talk-a / mouth-talk-o / mouth-smile 轮流）、挥手（arm-right-raise-* 抬手过渡帧 → arm-right-wave-* 来回 3 遍 → 放下）。以后多画过渡帧，只要按这个命名放进 `parts\` 并写进 `parts.json`，程序会自动用上；也可以在 `parts.json` 里写 `"animations": { "wave": [ { "frame": "arm-right-raise-1", "ms": 60 }, … ] }` 精确控制每一帧的时长。

   **设置**（右下角操作区的齿轮）：开机自动启动（登录后直接缩在托盘里，写在当前用户的启动项，不需要管理员）、安装 / 取消后台看门猫、自动更新公共规则、**界面主题**（「来生」红黑 + 荧光蓝，「摩羯」暗红 + 绯红、荧光绿点缀，「旧梦」黑紫 + 霓虹粉 + 荧光绿，切换后立即生效，存在 `data\settings.json`）、打开工具和数据文件夹。WatchDog 被 Windows 结束时（程序更新、卡住被关、重启后恢复应用）会被 Windows 重新打开；从别的应用（比如 Claude 桌面版这种商店应用）里启动时，它会自己通过资源管理器重新启动一次，免得那个应用更新时把它连带关掉。
9. **关掉再打开，之前的记录还在**：实时数据每 5 分钟和关闭时存到 `data/live.bin`（不进 git），打开时读回最近 1 小时的；更早的走势用看门猫的记录。中断不超过 30 分钟的程序，稳定性判断会接着之前的数据算。
10. **右键程序 → 用看门猫监控**：设一个内存上限，超过时提醒你或自动重启它。看门猫会专门记录它的走势。列表里带 ◉ 的就是被监控的程序。
11. **选中程序后，走势图右上角可以切换"内存 / CPU / 读写 / 句柄 / GDI"**。CPU、读写、GDI / USER 只有窗口的实时数据（30 分钟 / 1 小时）；看门猫的记录里每个程序有内存和句柄数。
12. **右键菜单**：顶部是程序名和稳定性，下面分「处理 / 诊断 / 监控 / 提醒」四组，每项带图标。**降低性能消耗**（节能模式）就是 Windows 11 任务管理器里的「效率模式」：把程序设成最低优先级并让 CPU 用省电方式跑它，程序照常运行（音乐不断、网页不掉线），游戏等前台程序要 CPU 时它会让路；再点一次恢复原来的优先级，WatchCat 退出时也会自动恢复。系统进程、外壳、输入法、音频、服务和 Claude 不能开。不冻结、不结束任何程序。
13. **右键程序 → 写备注说明**：给程序写一句自己的说明，会替换"说明"列里的默认说明。存在 `notes.json`（个人设置，不进 git）；清空备注就恢复默认说明。
13. **右上角"当前用户"**：点头像上传一张图片，点名称修改显示的名字（不是登录，只是展示）。下面显示电脑的系统版本、开机时间、已运行多久、CPU、显卡、内存和磁盘大小。头像和名字存在 `avatar.png`、`profile.json`（不进 git）。
14. **内核卡片**：显示驱动用的内存（分页池 + 非分页池）和全系统句柄总数，点它看走势（右上角切换"内存池 / 句柄"）。走势图下面列出占用最多、窗口打开后涨得最多的内存池标签。程序列表多了"句柄"和"GDI/USER"两列，可以点列标题排序。详见下面的"驱动泄漏、句柄和图形资源泄漏"。

## 看门猫在做什么

每 10 分钟在后台运行约 5 秒，然后退出，不常驻内存：

1. **按规则检查**：`rules.json` + `rules.local.json` 里 `auto: true` 的规则命中时自动修复（比如重启泄漏的托盘程序、重建 NVIDIA 数据库），其余只记录提醒。
2. **记录历史**：记下内存占用前 30 的程序、句柄最多的 10 个程序、规则 / 监控涉及的程序（每个程序记内存和句柄数），以及整机内存 / CPU / 磁盘 / 内核内存池 / 句柄总数，用来画 24 小时走势、判断长期稳定性。

## 稳定性评级

只看最近一次重启之后的数据（内存骤降 40% 以上或断档视为重启）。

**长期判断**（看门猫记录 ≥ 1 小时，10 分钟一个点）：

| 评级 | 条件 | 含义 |
|---|---|---|
| 疑似泄漏 | 每小时涨 ≥ 50 MB，累计 ≥ 100 MB，涨势稳定（R² ≥ 0.6） | 建议重启它 |
| 缓慢上涨 | 每小时涨 ≥ 15 MB，累计 ≥ 40 MB，R² ≥ 0.5 | 先观察 |
| 波动大 | 波动幅度超过平均值的 15% | 通常是正常使用（比如浏览器开关网页） |
| 稳定 | 以上都不是 | 占用再大也不算问题 |

**慢性泄漏**（看门猫记录最多 7 天，每小时取最低值）：有些后台服务没有任何新活动，却每小时只涨几 MB、几天下来涨了好几倍（比如外设、灯效软件的后台服务）。24 小时里看涨得慢，上面的标准抓不到，所以单独看 7 天：

| 评级 | 条件 | 含义 |
|---|---|---|
| 持续泄漏 | 至少 24 小时，几乎是一条直线（R² ≥ 0.95），"底线"（每 3 小时的最低值）90% 以上的时候都在往上抬，累计 ≥ 150 MB，且比开始时涨了 ≥ 50% | 建议重启它 |
| 缓慢上涨 | 至少 12 小时，累计 ≥ 100 MB，底线一直抬高（R² ≥ 0.85 且底线 85% 在抬高，或 R² ≥ 0.7 且底线 95% 在抬高） | 先观察 |

浏览器、聊天软件这类"开得越多占得越多"的程序会有起有落（R² 一般在 0.8–0.88，底线会掉下来），一般不会被判成持续泄漏；如果被判成缓慢上涨又确实是正常使用，点"正常"就不再提醒。

**浏览器**（Chrome、Edge、Firefox、Vivaldi、Brave、Opera、360、QQ 浏览器等）：内存跟着打开的网页和标签页涨落，大、忽高忽低都是正常的。所以浏览器的"缓慢上涨 / 短时上涨"不算问题（显示为"随网页涨落"），"疑似泄漏 / 持续泄漏"降为"涨得多"（黄色，先建议关掉不用的标签页，关了还降不下来再重启浏览器），一键修复也不会重启浏览器。选中浏览器时会写明这一点。

**短期判断**（窗口打开期间的实时数据 ≥ 10 分钟，5 秒一个点）：只给"短时上涨 / 波动大 / 稳定（初步）"，**不下"泄漏"结论**——程序在 10 分钟里涨一点往往是正常的（比如浏览器加载网页），满 1 小时才判断是否泄漏。

## 驱动泄漏、句柄和图形资源泄漏

程序列表看不到的两类"越用越卡"：

**驱动（内核内存）泄漏**：驱动申请的内存在内核的"分页池 / 非分页池"里，任务管理器的进程列表看不到，表现是总内存一直涨、但各程序加起来对不上。每个驱动申请内存时都带一个 4 个字母的"标签"，WatchDog 每 10 分钟拍一次按标签分开的明细（不需要管理员权限），所以能看出是哪个标签在涨；不认识的标签会在后台到驱动文件里搜一次，告诉你可能是哪个驱动（比如 `NVRM` → `nvlddmkm.sys · NVIDIA`）。

| 判断 | 条件 |
|---|---|
| 疑似泄漏（长期，本次开机以来看门猫记录 ≥ 3 小时） | 非分页池每小时涨 ≥ 15 MB、累计 ≥ 150 MB；或分页池每小时涨 ≥ 40 MB、累计 ≥ 400 MB；涨势稳定（R² ≥ 0.75） |
| 缓慢上涨（长期） | 非分页池每小时 ≥ 6 MB、累计 ≥ 80 MB；或分页池每小时 ≥ 15 MB、累计 ≥ 200 MB（R² ≥ 0.6） |
| 上涨中（实时，≥ 30 分钟） | 非分页池涨 ≥ 150 MB 或分页池涨 ≥ 300 MB，涨势很稳（R² ≥ 0.85）。只提醒观察 |
| 偏高 / 过高 | 非分页池 ≥ 2 / 4 GB，或分页池 ≥ 4 / 8 GB |

开机好几天后才开始漏的情况（比如屏幕唤醒后某个服务开始出错），放在"开机以来"的整段里会被前面平稳的几天冲淡，所以内核内存和句柄还会单独看**最近 3 / 6 / 12 小时**（要求更"直"：R² ≥ 0.85），取最严重的。内核内存在涨时，会列出**同时在漏句柄的程序**——句柄背后的对象都占内核内存，内核内存涨往往就是它们引起的。

处理：先看"同时在漏句柄"的程序，重启它们（下面有按钮）；没有的话，更新或回退最近装 / 更新过的驱动（显卡、网卡、杀毒、灯效、外设）。重启电脑可以立即收回。

**句柄和图形资源泄漏**：每个程序都记录句柄数和 GDI / USER 对象数。GDI、USER 单个进程上限 1 万个，用完了窗口、菜单就画不出来。

| 判断 | 条件 |
|---|---|
| 图形资源快用完 | 单个进程 GDI 或 USER ≥ 5000（黄）/ ≥ 8000（红） |
| 图形资源在一直涨（实时，≥ 20 分钟） | GDI 或 USER 涨 ≥ 500 个、每小时 ≥ 500 个、R² ≥ 0.85；已经 ≥ 3000 时算红色 |
| 疑似句柄泄漏（长期，看门猫记录 ≥ 2 小时） | 每小时涨 ≥ 500 个、累计 ≥ 3000 个、R² ≥ 0.7（缓慢上涨：≥ 200 个/小时、累计 ≥ 1500） |
| 句柄在一直涨（实时，≥ 20 分钟） | 涨 ≥ 3000 个、每小时 ≥ 3000 个、R² ≥ 0.85 |
| 句柄数异常多 | 单个进程 ≥ 5 万（黄）/ ≥ 10 万（红） |

发现句柄问题时，WatchDog 会在后台（最多每 10 分钟一次）数一下这个程序手里是**哪一类句柄**，写在问题说明最前面，这是找原因最直接的线索：比如"注册表键 6 万多个"说明它反复打开注册表不关，"线程 + 事件"说明它不停新建线程却不释放，"桌面"一般和显示器开关、切换有关。

**自动记录现场**：句柄在暴涨时，看门猫（以管理员权限运行）会自动把现场记下来，存在 `data\incidents\` 里的一份文本（只在本机）。连续两次检查都在涨、而且最近 10 分钟涨得多才会触发，同一个程序 1 小时最多记一次，最多保留 40 份。记录里包括：
- 每类句柄多少个；注册表键 / 事件 / 共享内存的**具体名字**（同名的合并计数）——能直接看出它在反复打开哪个注册表项；
- 线程句柄：线程是否已经结束、**从哪个模块启动**（比如 NVIDIA 的某个插件 DLL）；进程句柄指向谁；
- 这个进程加载的第三方模块和版本、最近 12 小时的熄屏 / 亮屏 / 睡眠事件、最近 2 小时的服务崩溃和新装服务、最近 1 小时启动的程序、内核内存池最大的标签。

也可以手动：右键程序 → "立即记录句柄现场（管理员）"，或运行 `Capture-Handles.ps1 -Name 程序名`。已经记过的问题，说明里会标"已记录现场"，右键可以打开最近的一份。只读：只复制句柄来查询，不改动任何程序。

这类问题重启那个程序就能释放（如果它是系统服务，会按服务重启，需要管理员确认）；"一键修复"会重启红色的那些（系统关键进程除外，比如 `System` 的句柄一直涨通常是驱动引起的，只能重启电脑）。也可以"忽略"或"确认正常"。

## 自动重启出问题的那一小块（并核对重启前后一致）

漏掉的内存没法从外面清掉，在厂商修好之前，看门猫会在它们涨过上限时**只重启出问题的那一小块**：

| 规则 | 超过多少 | 怎么重启 | 重启后核对什么 |
|---|---|---|---|
| 华硕 Aura 灯效（`LightingService`） | 400 MB | 重启灯效服务，**再重启奥创中心服务**：灯效服务重启后只记得模式、不记得你的灯效脚本，脚本要奥创中心重新下发（它只在自己启动或屏幕点亮时才发） | 灯效服务在运行、它的日志里出现了重启**之后**新收到的灯效脚本（`put_SetScript`） |
| 海盗船 `CorsairCpuIdService` | 500 MB | 重启这个后台服务 | iCUE 还在、服务日志里出现"有新连接 / 设备列表更新"（iCUE 重新连上了） |
| 罗技 `lghub_agent` | 1.5 GB | 关掉 agent 和托盘，按开机方式（`--minimized`，不弹窗口）启动托盘，由托盘带起 agent | 托盘和 agent 都在 |
| 罗技 `lghub_system_tray` | 500 MB | 只重启托盘（同样带 `--minimized`） | 托盘和 agent 都在 |
| Steam 网页界面（`steamwebhelper`） | 2.5 GB | 只关掉网页进程，Steam 会自己重新拉起；Steam 本身、下载、登录都不动 | Steam 主进程还是原来那个、网页进程回来了 |
| Windows 音频服务 / NVIDIA 显示容器 | 300 MB / 1.5 GB | 重启服务 | 服务在运行（NVIDIA 还要显示容器进程在） |

- **只在你不用电脑时动手**：10 分钟以上没碰键盘鼠标才执行（规则里的 `idleMin`），灯效闪一下、声音断两秒你都碰不到；正在用就等下一次检查。Steam 还要求没在玩游戏（常驻的桌宠、动态壁纸不算游戏，见 `notGames`）。
- **核对不通过就补救一次**：服务又停了就再启动一次，程序没回来就按原来的路径和参数再启动，然后再核对；还不行就在日志里记"核对失败"。
- **每次都有记录**：日志里一行 `DONE`，写着重启前 → 后的内存和核对结果。在"操作"里点 **修复记录** 可以看全部记录（处理前后的内存、核对结果；句柄现场记录和内存分析双击打开）。

作者电脑上实测（2026-11-17）：海盗船 1,207 → 42 MB（8 秒恢复，iCUE 重新连上）；Aura 620 → 13 MB（第一次只重启了灯效服务，灯效变成了默认彩虹；改成同时重启奥创中心服务后，10 秒内恢复成原来的灯效）；G HUB 1,233 → 107 MB（2 秒，托盘和后台都回来了）；Steam 网页 3,782 → 1,097 MB（12 秒，Steam 本身没动）。

**专项修复**："操作"里的荧光蓝卡片 **专项修复** 把所有针对某个程序的修复放在一个列表里，一个程序一张卡片：它现在多大、离上限还有多远、为什么会涨、看门猫最近一次做了什么；可以立即修复、改设置，有分析报告的可以直接打开。

**看和改规则**："操作"里点 **规则设置**（或专项修复卡片上的"设置"），能看到全部规则、每条最近一次做了什么；选中一条可以改上限、空闲多少分钟才动手、超过上限时自动处理还是只提醒、启用还是关闭。修改存成 `rules.local.json` 里同 id 的一条（覆盖公共规则，`rules.json` 不动），"恢复默认"就是删掉这条覆盖。看门猫下次检查（最多 10 分钟）就按新的来。新加监控：右键程序 → 用看门猫监控。

核对只看重启**之后**新写进日志的内容，旧记录不算。规则文件里：`fix.args` 是重新启动时用的参数，`verify` 是重启后要核对的东西，`disabled: true` 关掉一条规则。

## 找出内存为什么一直涨

选中一个在慢慢涨的程序 → 点 **分析内存泄漏**（右边"选中的程序"里，右键菜单也有）（需要管理员确认，约 1 分钟），结果用记事本打开，也存在 `data\incidents\` 里。报告开头有一段自动解读，下面是依据：

- **它在忙什么**：观察 10 秒，找出一直在耗 CPU 的线程；每 0.1 秒让它暂停约 1 毫秒、读一次调用栈，抓几十次，统计时间花在哪个 DLL 的哪个函数。电脑没人用时还在忙，说明它在后台不停地轮询——一直涨的内存多半就是这个循环每转一圈漏下的。
- **漏的是什么**：把它的私有内存读一遍，统计重复最多的字符串。正常程序不会把同一份数据存几万遍；重复了几十万次的，就是"每次生成一份新的、旧的没释放"的那份数据。
- **涨多快**：从看门猫的记录算最近 24 小时的上涨速度和平均 CPU。

为什么不能"从外面把漏掉的内存清掉"：漏掉的内存还在程序自己的内存池里，从外面分不清哪块已经没用、哪块还在用，硬释放会让它崩溃。根治靠厂商修复，或者关掉 / 换掉触发泄漏的功能；临时办法是让看门猫在它涨过上限时自动重启它（右键 → 用看门猫监控）。

作者电脑上用它查到的例子（2026-11）：
- 海盗船 `CorsairCpuIdService`（iCUE 5.46.67）：每约 1.5 秒把整台电脑的硬件 + 传感器清单生成一份（约 4 KB）发给 iCUE，旧的不释放——1.2 GB 内存里同一份清单存了 29 万份。
- Steam 主界面的网页进程：游戏库页面反复重新生成所有游戏卡片，"library_600x900.jpg"等内容存了 15 万份以上，涨到 3 GB。
- 华硕 `LightingService`：Aura Sync 的动画脚本由它用软件逐帧计算、通过 SMBus 写给内存条的灯（约 64 毫秒一帧，一直占 20% 的一个核），内存每小时涨约 5 MB；把内存条灯效改成静态或硬件自带效果即可绕开。
- 罗技 `lghub_agent`：反复建立到 Windows 音频服务的连接（127 万份连接名），并保存了几千份所有进程的启动命令（自动识别游戏在扫描进程）。

## 问题规则库

每条规则写明症状、原因和修复方法，例如：

```json
{
  "id": "lghub-tray",
  "title": "罗技 G HUB 托盘泄漏",
  "target": "lghub_system_tray",
  "when": { "process": "lghub_system_tray", "minMB": 800 },
  "cause": "G HUB 托盘程序的已知问题……重启它不影响鼠标键盘的设置和灯效。",
  "fix": { "type": "restartProcess", "label": "重启 G HUB 托盘" },
  "auto": true
}
```

- `when`：`process`（进程名；`svc:服务名` 表示承载该服务的进程）+ `minMB`，和/或 `file` + `minFileMB`。条件全部满足才算命中。
- `fix.type`：`restartProcess` 重启程序 / `restartService` 重启服务 / `restartGroup` 按顺序重启一组（`fix.steps`：`{ "service": "名字" }` 或 `{ "process": "名字", "args": "启动参数" }`，由 `Restart-Group.ps1` 执行）/ `script` 运行本目录下的脚本 / `none` 只提醒。
- `rev`：规则的版本号。在线更新下来的规则只有 `rev` 比自带的大才会替换同 id 的规则。
- `auto: true`：看门猫会自动执行修复；`false` 只在窗口里提醒。
- 没有命中任何规则、但被评为"疑似泄漏"的程序，可以在窗口里直接重启（通用修复，见下）。

### 没有专项规则的程序怎么处理（每台电脑都适用）

1. **记下它是怎么启动的**：窗口开着时，每分钟顺手记 2 个程序（重点监控的、有问题的、内存最多的）的启动参数和"由谁启动"（读一下命令行，很轻），存在 `data\launch.json`。
2. **先试最小的范围**：重启时，如果它是同一个软件的主程序带起来的（比如 Steam 带起 `steamwebhelper`），只结束它，等主程序把它拉起来；没被拉起来、或者它本来就是独立的，就**按原来的路径和参数**重新打开（比如 G HUB 托盘的 `--minimized`，不会弹出窗口）。是服务就重启服务。
3. **核对**：等它回来，看内存降了多少；没回来会告诉你。手动重启也会记进"修复记录"。
4. **问一次正不正常**：第一次重启某个程序后会问"现在一切都正常吗？"（设置、登录状态、灯效、窗口……）。正常的以后可以放心重启；不正常的，一键修复以后不再动它，并引导你建一条专门的规则。答案存在 `data\restart-feedback.json`。

### 规则向导：在自己电脑上做专项修复

右键程序 → **为它建修复规则**（第一次重启后说"不正常"时也会引导过来）。向导会列出它的路径、启动参数、由谁启动、厂商、是不是服务，以及**同一个软件 / 同一家厂商**正在运行的服务和程序（比如华硕灯效服务和奥创中心服务装在不同目录，但都是华硕的）。处理方式三选一：只重启这个程序、重启服务、**按顺序重启一组**（先它，再勾选的）。先点 **试一次**，看效果正常再 **保存规则**（存进 `rules.local.json`，默认只提醒；试过几次都正常再打开自动处理）。**保存并分享**会把规则复制到剪贴板（个人路径换成 `%USERPROFILE%`），并打开 GitHub 的新 issue 页面，粘贴进去就能分享给其他人；审核后会合并进公共规则。

### 公共规则在线更新

`rules.json` 是自带的公共规则。设置里的 **自动更新公共规则**（默认开）每天从 GitHub 取一次最新的 `rules.json`，存成 `data\rules.remote.json`，窗口和后台看门猫都会用。只下载规则文件，不上传任何东西；要运行的修复脚本本机没有的规则会跳过。设置里也可以点"立即更新规则"。

目前内置的规则（10 条，都在作者电脑上验证过）：NVIDIA 数据库膨胀、NVIDIA 显示容器占用过高、Windows 音频服务泄漏、罗技 G HUB 托盘泄漏、罗技 G HUB 后台泄漏、华硕 Aura 灯效服务泄漏、海盗船 iCUE CPU 信息服务泄漏、Steam 网页界面泄漏、BongoCat 占用过高、Hue Sync 占用过高。欢迎提交新的规则。

### 不知道怎么处理：生成问题报告发给开发者

右键程序 → **生成问题报告**（规则向导里也有这个按钮）。会在 `data\reports\` 生成一份文本报告：程序的路径、版本、厂商、启动参数、由谁启动，同一个软件 / 同一家厂商正在运行的服务和程序，最近 24 小时和 7 天的内存走势、句柄走势，WatchDog 的判断、相关规则、重启后的反馈、看门猫的记录，以及之前做过的内存分析报告。用户名、电脑名、个人目录都换成占位符。报告只存在本机，不会自动上传；点"去 GitHub 提交"会打开新问题页面，把文件拖进去就能发给开发者，开发者据此写一条公共规则，之后通过在线更新所有人都能用上。

## 自身占用（作者电脑实测，16 核）

| 部分 | 什么时候运行 | CPU | 内存 |
|---|---|---|---|
| 后台检查 `MemWatchdog.ps1` | 每 10 分钟一次，约 5 秒 | 每次约 1 秒 CPU 时间，平均约占整机 0.01% | 运行时峰值约 100 MB，结束后全部释放 |
| 监控窗口 `WatchDog.exe` | 打开或在托盘里时 | 约 0.1% | 约 50–58 MB，退出即释放 |

## 自身不会泄漏

- 看门猫每次运行几秒，检查完就退出，不常驻内存。
- 读取进程读写量、GDI / USER 数、程序路径时，系统句柄打开后立即关闭（读写量和 GDI 共用一次打开）；磁盘计数器只打开一次，关窗时关闭；程序图标缓存最多 150 个。
- 实时数据存在固定大小的环形缓存里：每条最多 720 个点（1 小时），最多 320 条，满了覆盖最旧的；15 分钟没出现的程序会被清掉。句柄 / GDI 只记最多的 15 个程序（加上有问题的和选中的）。
- 内存池明细只存排好序的数组（每张约 40 KB），最多 8 张（窗口打开时一张 + 最近 1 小时每 10 分钟一张）；搜驱动在后台线程里做，每个标签只搜一次，用 1 MB 缓冲区分段读，不把驱动文件整个读进内存。
- 列表原地更新（只改变化了的格子），不清空重建，也不先擦背景再画，所以不会闪，滚动位置也不会跳。
- 监控窗口在打开或缩到托盘时运行（托盘里只记录、不画界面），所有临时数据每次刷新整体替换；底部实时显示窗口自身占用。
- 实时数据存盘文件大小有上限（最多 320 条 × 720 个点，约 2.8 MB），先写临时文件再替换，写一半断电也不会坏。
- 所有画笔 / 画刷 / 字体只在启动时创建一次，绘制时复用，避免 GDI 资源泄漏。
- 自测：`WatchDog.exe --selftest --loops 1800 --sim 60` 在屏幕外连续刷新并完整重绘 1800 次（约等于开着窗口 2.5 小时），每 150 次记录一次，结果写到 `selftest.txt`：实时数据缓存一开始就填满 1 小时；自身内存一直在 60–61 MB、不往上涨（读入 7 天的看门猫记录后），托管堆始终 4.5 MB，GDI 对象始终 94，句柄数在 490–506 之间、不增加。另外用每秒约 80 帧的连续截屏检查过刷新时列表不闪。
- 历史数据每天约 380 KB，只保留 7 天。超过 25 小时的旧记录文件不会再变，读一次后只留按小时的汇总（每个程序每小时一个点），之后不再重读。
- 数句柄类型时要读一次全系统的句柄表（30 多万个句柄约 13 MB），只在发现句柄问题时由后台线程最多每 10 分钟做一次，用完立即释放。

## 已知的泄漏来源（作者电脑上实测）

- **NVIDIA NVDisplay.Container**：`nvtopps.db3` 膨胀到 2 GB+，导致容器占用 8 GB 内存并持续读写硬盘。重建数据库后降到约 24 MB。
- **Windows 音频服务（Audiosrv）**：装有 Sonic Studio / Nahimic 时长时间运行可涨到 2 GB+。
- **罗技 G HUB 托盘程序**（`lghub_system_tray`）：长时间运行可涨到数 GB。只重启托盘，不影响设备设置。
- **慢性泄漏的外设 / 灯效后台**（7 天记录，几乎是直线）：海盗船 `CorsairCpuIdService` 5 天 124 MB → 1.2 GB（约 9 MB/小时）；罗技 `lghub_agent` 237 MB → 1 GB（约 6 MB/小时）；华硕灯效 `LightingService` 17 MB → 614 MB（约 5 MB/小时）。
- **屏幕唤醒后的连锁句柄泄漏**：屏幕熄灭几小时后再点亮，之后华硕 `ROG Live Service`（3.7.6）开始反复打开注册表键不关，4 小时攒了 6.7 万个；同时 NVIDIA 的 `nvcontainer` 不停新建线程不释放（线程 1.8 万 + 事件 1.8 万），`NVDisplay.Container` 的桌面句柄也一直涨。内核分页池 4 小时涨了 1.6 GB（主要是图形内核 dxgkrnl 的 `VdPN` 和 `Gpbm` 标签）。不是每次唤醒都会发生。重启这几个服务即可；不需要 ROG Live 的推送功能可以把这个服务设成"手动"。
